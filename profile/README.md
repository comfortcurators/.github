# Comfort Curators

**Governing software for heterogeneous systems.**

Comfort Curators Private Limited builds software that observes, compares, governs and learns across models, runtimes, infrastructure and real operational workloads.

The company is not organized around a single model, cloud or application category. The common problem is coordination: how a system knows what exists, what each source says, where sources disagree, what action is actually permitted, and whether the outcome verified the decision.

## The work

| System | Role |
| --- | --- |
| **SuperhostOS** | A governing runtime for heterogeneous compute and operational systems. Hospitality is its live proving ground, not its identity. |
| **Curator** | Long-term memory, comparison, judgment and implementation kernel. It preserves agreement, conflict, tails and recurring patterns instead of reducing every decision to a vote. |
| **comfort-ci** | The organization’s CI/CD authority: admission, durable queueing, isolated execution, deployment and exact-commit verification. |
| **Host** | The public company surface: product, research, governance and the operating-stay interface. |
| **Curatory** | An isolated spatial documentation laboratory for making systems, evidence, provenance, authority and history legible. |

Most platform repositories remain private while the systems are under active development. Public presentation should not be mistaken for the complete execution surface.

## Operating principles

**Source before story.** A configuration, commit or log is evidence of a particular kind; it is not automatically proof of a deployed or successful outcome.

**Disagreement is information.** Curator preserves four result domains independently: **agreement, conflict, tail and pattern**. Rare or contradictory possibilities are not erased because a majority is convenient.

**Action must close the loop.** Intent → decision → execution → real outcome → verified learning. A queued request or recorded intention is not success.

**Authority stays explicit.** Product repositories can contain application code and validation commands without each becoming its own deployment authority.

**Uncertainty remains visible.** Unknown, declared, planned, contradicted, legacy and verified states should not collapse into the same visual or operational status.

**Secrets do not become documentation.** Architecture may name credential contracts; secret values do not belong in repositories, examples, logs or public diagrams.

## A useful mental model

```text
observe
  ↓
retrieve what is already known
  ↓
ask native sources
  ↓
compare agreement / conflict / tail / pattern
  ↓
apply deterministic constraints
  ↓
propose and authorize action
  ↓
execute through the correct system
  ↓
record the real outcome
  ↓
learn only from verified evidence
```

The visualization, dashboard or model is never the authority merely because it is easier to look at. Source systems keep their own truth; the observing layer makes that truth easier to inspect and reason about.

## Why hospitality appears here

Comfort Curators operates against real hospitality workloads because they force software to deal with messy reality: people, calendars, geography, language, pricing, maintenance, communication, external platforms and consequences that cannot be simulated away.

That workload is a proving ground for the governing runtime. It is not the boundary of the underlying systems work.
